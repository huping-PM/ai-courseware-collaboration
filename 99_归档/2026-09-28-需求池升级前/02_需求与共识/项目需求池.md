# 项目需求池

维护日期：2026-09-28。用途：收集日常业务需求，供后续统一澄清、产品设计、规划及开发安排使用。本文是本地需求收集主本，收录不代表业务方案已确认或已承诺开发。

## 使用方法

- 新需求先记录原话、来源、场景、期望结果；信息不足可先入池，不要求先写完整PRD。
- 收集编号使用“收集001”顺延，删除或合并后不复用。它不是正式R需求编号；进入正式需求分析时关联已有R编号，确需新增时沿用项目R编号顺延规则。
- 同类反馈合并到已有条目，保留新增来源及差异；不重复创建同义需求。
- 优先级、版本、负责人、工时和日期须有确认依据，未知则标“待定”。不按收集顺序推定优先级。
- 后续按需推进：待澄清 → 待规划 → 设计中 → 待评审 → 待排期 → 已排期 → 开发中 → 待验收 → 已完成；也可暂缓、取消或合并，记录原因。每次状态变化附依据，禅道创建成功不代表已排期或已开发。
- 正式设计、评审和实施材料形成后在条目中链接，不在本池复制整份正文。业务决定仍按项目规则同步共识及决策台账。

## 收集004：技能保存后自动运行验证

- **用户原话：** “创建和编辑技能时，点击确认后，技能自动进入验证中状态，后台验证技能是否可以跑通，根据验证结果更新技能状态，验证通过，验证不通过”。
- **来源与收集日期：** 用户本次会话，2026-09-23。
- **业务模块与场景：** 技能管理；维护人员创建或编辑技能并确认后，需要知道该技能能否实际运行，而不只知道文件能否解析。
- **期望结果：** 确认创建或编辑后，技能进入“验证中”；后台执行可运行性验证，再按结果更新为“验证通过”或“验证不通过”。
- **既有设计关联：** [AI课件协作平台-需求说明 §3 提交与解析状态](../03_功能设计/AI课件协作平台-需求说明.md#3-提交与解析状态)当前写有“解析中→启用/解析失败”，并明确上传时只解析、不执行脚本。本条提出实际跑通验证，需在产品设计时明确它与文件解析、启用/停用、全局/项目专属状态及审批规则的关系；现有设计未据此直接改写。
- **待澄清：** “点击确认”是在表单保存后还是审批通过后触发；编辑技能时验证的是新版本还是直接替换当前可用版本，验证期间原版本能否继续使用；“跑通”的输入、环境与通过标准；验证超时或异常如何展示和重试；验证通过是否自动启用，验证不通过时是否保留原版本及失败原因。这些决定影响实现与验收，当前不替用户预设。
- **状态与安排：** 待澄清；优先级、版本、负责人、工时均待定，尚无正式R编号、评审或排期依据。
- **下一步：** 在技能管理功能设计阶段先定义验证对象、触发时机和状态关系，再形成评审稿与可执行验收标准。
