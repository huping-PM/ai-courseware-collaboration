### 1.1 每项必备信息

| 字段 | 填写要求 |
|---|---|
| 编号、名称、模块、父需求/关联编号 | 保留稳定编号；不同来源同一诉求合并关联，跨域需求只设一个主要维护入口 |
| 提出时间、提出人、来源 | 提出时间必须有直接依据；无法证明首次提出时写“待核实”，另列可证记录日期；用户姓名未知时只写“用户” |
| 登记时间、最近更新 | 既有入池日期保留；本轮补录不倒填历史入池日期；更新只代表台账核对时间 |
| 问题/目标、需求详情、范围边界 | 至少能看出谁在什么场景做什么、系统如何响应；详细字段/流程/异常链接正文 |
| 业务确认、需求状态、产物状态 | 分栏记录，不能以原型完成代替评审通过 |
| 优先级、目标版本、负责人、估时及计划日期 | 有确认才填值；未知为待定。提出人、建议指派人不自动视为研发负责人 |
| 实施、测试、验收及上线 | 有实际证据再更新；本地无证据写“待核实”，不据此断言团队尚未工作 |
| 依赖/待确认、验收口径、下一步 | 关联原Q编号；不重复设另一套问题状态 |
| 变更依据与关联产物 | 保留确认、设计、排期、禅道、验收入口及版本；取消/合并保留原条目和去向 |

**全表默认值（每项适用，条目另有记录时覆盖）：** 本轮台账核对时间2026-09-28；优先级、正式目标版本、产品/研发/测试负责人、工时、计划开始/完成日期、实际上线日期均待定；研发/测试/业务验收/上线状态均为“待核实，未取得本轮核验依据”。I01—I08属于已确认的迭代需求集合，不等于已确认发布日期。用户指定的蔡博、曾凡圆单独保留为指派依据，不推定工时或开工。

### 1.2 状态怎样更新

| 需求状态 | 进入依据与后续动作 |
|---|---|
| 待澄清 | 目标已收录但关键规则不足；补齐影响设计/验收的问题 |
| 待规划 | 需求可讨论但是否进入版本未决定；记录纳入决定，不自动赋优先级 |
| 设计中 | 有已授权设计工作和在制产物；业务规则与设计建议分开 |
| 待评审 | 已有可审阅需求或设计；注明待评审对象，需求已确认但原型待评审可并存 |
| 待排期 | 已有业务确认依据，尚缺正式计划；历史入池状态可保留并标明核验边界 |
| 已排期／开发中／待验收 | 分别需要正式排期、研发进展、实际交付及测试证据，不靠文档更新时间推定 |
| 已完成 | 按约定范围业务验收通过并链接验收记录；上线信息另记 |
| 暂缓／已取消／已合并 | 记录决定日期、理由和去向；历史方向未纳入当前范围不自动称“暂缓” |

需求域内子项进度不一时标“分项管理”。状态变更写入第7节，记录原状态、新状态、日期和依据。只有文档没有实测时，不使用“功能已实现”。
