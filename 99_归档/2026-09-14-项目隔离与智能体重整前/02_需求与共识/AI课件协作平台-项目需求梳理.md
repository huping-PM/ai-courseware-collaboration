## 1. 整体判断

本项目是面向公司内部培训内容生产的AI协作平台：以项目组织资料、人员和任务，以对话工作台推进制作，以共享技能、模板和模型能力支撑生成，以人工确认控制质量，以阶段成果和素材沉淀支持续做与复用。

会议明确了两个相互关联的目标：

1. **业务生产目标：** 把个人电脑上分散的制作流程搬到内部平台，减少反复切换、复制资料和重复摸索规则，在可接受质量下改善制作效率。（12:42、17:35、27:12）
2. **团队协作目标：** 以本项目试行产品、研发、测试的AI协作，形成共同业务理解、明确分工和生成—检查—人工验收的方法，考察实际产出和效率改善。（01:29:16—01:40:57）

当前最具体的业务样例是“情景动画＋知识讲解视频”的组合课件。情景动画承担故事和场景表达，知识讲解承担知识点呈现；脚本确认后分两条制作线，最后合成。项目整体需容纳多种内容形式，但会议没有承诺首版同时实现全部形式。（00:00、14:10—15:42、01:13:16—01:16:30）

最关键的产品判断：需要同时定义“整条课件怎样完成”和“首版哪些步骤在平台内完成”。情景部分允许外部工具过渡、知识讲解部分先跑通，是会中的收敛意见；最终是否允许这种组合交付、如何回传与合成，仍需Q11确认，不能把仅生成文稿称为完成课件生产。

## 2. 业务现状、问题与价值

| 会议中的现状或问题 | 应转化的产品需求 | 预期价值与证据边界 |
|---|---|---|
| 同事在个人电脑和多个工具上操作，资料及规则各自保存（02:04、07:11、17:35） | 项目空间、共享资料、统一技能、阶段成果承接 | 减少传递和查找；尚无工时基线 |
| 文字环节已有规则，选题可产出含口播的脚本（01:09、01:09:30） | 将已验证文字方法接入并支持人工修改 | 优先承接已有业务方法；需取得真实样例验证 |
| 知识讲解像静态PPT翻页，停留长、动效不满意（03:01、12:06、01:21:58） | 知识点拆解、画面生成、节奏与讲解声音组合、预览修改 | 好坏应通过业务样片定义；不是指定生成.pptx即可验收 |
| 角色/场景不稳定，同镜头反复生成（11:10、46:43—49:31） | 可引用角色和场景、预览选择成果、可定位返工 | 平台可帮助保留依据；不能保证生成一次成功 |
| 短样片规则到长视频被遗忘（18:47—20:41） | 共享规则可持续引用，修改反馈能回到技能 | 需要核验执行效果；不是“保存技能即零错误” |
| 字幕与声音匹配、字体/位置调整依赖外部工具（22:11—24:53） | 明确字幕制作、校验、导出和外部操作边界 | 识别文字不等于完成字幕时间匹配与编辑 |
| 多人AI开发可能重复生成、风格不一致、成果难合并（01:35:45—01:38:48） | 团队工作分工、共享上下文与检查方法 | 属于项目执行要求，不自动新增平台研发管理模块 |

降本、提效、规模化延续旧共识，但会议中的“每分钟多少钱”等试用数字涉及不同模型、质量和重做次数，不能合并成成本基线，更不能承诺降本比例。

## 3. 项目框架

以下是产品能力组织框架，便于拆需求；不表示菜单已确定，也不预设技术栈或数据库结构。

| 层次 | 包含内容 | 作用及关联需求 |
|---|---|---|
| 业务组织 | 项目、共同目标与受众、课程/视频任务、参与者 | 明确做什么、归哪里、谁处理；R01、R06、R07、R11 |
| 制作入口 | 项目内对话、引用资料/技能/成果、旁侧预览与修改、人工确认 | 把操作和阶段成果连起来；R03、R05、R08 |
| 生产过程 | 文字内容 → 脚本确认 → 情景动画/知识讲解两条线 → 合成与审核 | 形成可交付内容；R03—R05、R12 |
| 可复用依据 | 项目/公共资源、模板或风格方案、技能及规则 | 统一制作方式和素材；R02、R09—R11 |
| 执行能力 | 文本、图片、视频、语音模型；字幕和合成工具；必要的外部工具衔接 | 执行各节点、支持替换与适配；R04、R14 |
| 质量与持续改进 | 阶段确认、问题反馈、返工、有效规则沉淀、字体及效果约束 | 保证能检查、能修改、能续做；R05、R15 |

框架依据：27:12—32:13、35:33—35:58、01:07:52—01:16:30；“分层”是分析组织方式。

### 3.1 项目空间与公共能力

- 项目空间保存项目背景、受众、资料、IP人物、场景、样片及制作成果。会议举例包括文档、视频、音频、图片、片头片尾。（27:12—28:20）
- 公共范围保存跨项目通用资料和技能；项目内保留专用或适用内容。访问规则、公共与项目同名规则的优先关系待确认，不套用其他工具的实现。（28:20—29:06）
- 会议表示依托内部资产管理系统搭建，说明这是新业务平台建设与已有基础系统结合的方向。工作区截图是否就是该系统、哪些功能已经可复用，仍须Q01核验。（27:12、01:04:36）
- 受众和目标可以由项目背景继承，不必每条课程重复填写；具体课题和差异仍需表达。继承、覆盖与更新方式待设计。（01:16:06—01:16:30）

### 3.2 需要分清的对象

| 对象 | 业务含义 | 容易混淆之处 |
|---|---|---|
| 资源/素材 | 文档、IP参考图、场景、音频、片头片尾等输入或产物 | 存有素材不代表每次生成自动使用，需要明确引用 |
| 模板/风格方案 | 预期长什么样、采用何种内容结构和制作方法 | 使用者可能以“技能”称呼模板；是否合并入口待确认，不能直接改成一对一 |
| 技能 | 某类工作怎么做、如何检查的可复用规则 | 一个阶段可调用多个技能；同一技能也可跨阶段复用 |
| 模型 | 实际生成文本、图片、声音或视频的执行能力 | 官方网站完整功能、模型接口、平台交互能力不能等同 |
| 流程节点 | 某一步的输入、动作、输出及人工确认点 | 宏观节点不必与每个技能一一对应；本次梳理不承诺可视化流程编辑器 |
| 阶段成果 | 已生成、正在修改或已确认的文稿与媒体 | 保存不必然等于确认；确认哪一版、后续引用哪一版需明确 |
| 任务/会话 | 组织一条内容的制作与对话 | 项目级空间已表达，单任务会话边界、多人同时编辑和隔离规则仍未定 |

## 5. 完整业务流程

### 5.1 通用生产主线

项目背景与共享资料 → 确定本次课题及呈现方式 → 引用模板/技能生成文字 → 人工修改并确认脚本 → 按内容分段进入制作路线 → 汇集所需片段并合成、处理字幕 → 人工审核与返工 → 保存和交付 → 将可复用经验完善为技能/模板。

依据：12:42—17:35、27:12—32:13、01:08:38—01:16:30、01:43:25。最终交付和整套验收沿用旧共识，具体交付对象与包内容未在本次会议定清。

### 5.2 内容环节

| 阶段 | 输入 | 产出和人工动作 | 确认边界 |
|---|---|---|---|
| 建立/进入项目 | 业务背景、对象、目标、共同资料 | 可重复引用的项目依据 | 前置信息可在项目中维护，不要求每课重填 |
| 提交课题与选用方案 | 选题/知识点、必要参考资料、模板或技能 | 本条课程的内容要求 | 没有资料时可补充或辅助检索；资料真实性需内容人员判断 |
| 生成及修改文字 | 上述输入和文字技能 | 口播、对白、人物/场景描述及脚本内容 | 现有实践可能一次产出含口播的脚本；不得强制新增重复文档 |
| 确认制作输入 | 经修改的文字成果 | 能被下游引用的已确认脚本 | 是否单设文案确认、分段确认，见Q02 |

会议01:09:30—01:10:19表明“文案—脚本—分镜”不一定对应三个独立文件。旧共识要求独立保存和分别确认，当前应保留差异，先拿一份真实脚本和分镜核对。

### 5.3 脚本后的两条制作线

两条线服务于同一条组合视频的不同片段，不宜建模成只能二选一。单一知识讲解等其他形式是否可单独交付，及首版路线选择方式，见Q11。

| 制作线 | 输入 | 主要步骤 | 产出/确认 | 来源与不确定性 |
|---|---|---|---|---|
| A 情景动画 | 脚本中的情景段、角色参考、场景与风格 | 拆分并调整分镜/提示词 → 准备角色/场景图等制作依据 → 生成镜头 → 人工预览、筛选或重做 | 可用于合成的情景片段；场景内对白/声音可能随片段生成 | 43:33—46:43、01:10:19、01:13:16、01:15:31；参考图与提示词如何组织、语音分工、是否外部制作待确认 |
| B 知识讲解视频 | 脚本中的讲解段、知识点、口播、风格方案 | 拆解文字与知识点 → 生成讲解画面/PPT等中间成果 → 制作动画视频并匹配讲解声音 | 可用于合成的知识讲解片段 | 29:52、01:13:54—01:15:31；独立分镜不是已确认必经步骤，配音与画面先后关系待实样核对 |
| 合流 | 两条线实际所需片段及声音 | 汇集与合成 → 字幕生成/时间匹配和样式处理 → 整体检查 | 最终视频及其制作依据 | 22:11—24:53、01:14:51—01:15:31；字幕在哪一层处理、合成工具和回传格式待确认 |

“PPT”在会议中既指现有制作方式，也泛指知识讲解画面。业务关心知识表达、动效和节奏，最终产出为视频；不能据此锁定PPT文件为唯一中间格式。SVG/H5等是效果试验建议，尚非技术选型。（01:22:31—01:26:21）

### 5.4 每个阶段的人工闭环

生成结果 → 人查看/修改 → 确认当前成果 → 将该成果作为下一步输入。结果不满意时留在当前环节迭代，不直接一路生成到底。（15:42—16:38、31:32、01:08:38）

应在设计时补齐的规则（分析建议）：

- 明确“保存”和“确认继续”的含义，避免一次文字保存意外启动昂贵生成。
- 上游已确认内容修改后，让人识别受影响下游并决定重做；不自动承诺联动重生成。
- 重试或生成失败时保留此前已满意的成果，能说明本次问题在哪一步。
- 外部制作时记录输入出处和回传成果归属，让任务可以继续；不能只有跳转链接而丢失后续交接。
- 制作反馈分为本条内容修改和共享规则改进，避免一个课题的临时要求改变所有项目。

上述属于R03—R05、R08—R11的待设计规则，不是会议已定的详细交互。

### 5.5 系列课程流程（继承旧共识）

确认课程目标与目录 → 选择一条试制 → 确认首条及共同制作依据 → 逐条或分工制作 → 系列整体审核 → 保存交付。

会议主要细化了单条内容制作，没有重新确认目录层级、批量启动、人员分配或整套验收。R06、R07、R12、R13继续保留；不得以这次未提及为由删除，也不得以整体规划存在为由全部纳入首版。

### 7.2 分期候选（分析建议，待Q09/Q11确认）

| 范围 | 建议如何讨论 | 原因 |

### 7.3 必须保留的取舍

- 便利性与可用性：对话式可以先落地，但若无法引用角色、调整文字、查看媒体或承接下一步，业务仍可能用不了。
- 质量与成本：反复生成及局部编辑会影响费用和周期；先建立相同质量要求下的验证口径，再比较。
- 标准化与灵活性：共享技能保证共同依据，初期仍需试选模型和修改规则；固定时机需业务验证。
- 通用框架与首条流程：项目框架容纳多业务；第一条流程可具体，不必先构建复杂通用编排系统。
