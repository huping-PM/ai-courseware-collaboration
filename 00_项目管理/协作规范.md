## 2. 一次任务怎样推进

1. **定位：** 读取根规则、项目状态和本次涉及的依据，确定要求是分析、起草、设计、评审还是执行。
2. **明确边界：** 继承已确认事项；识别信息缺口。只有影响当前结果的必要问题才向用户提出，其余进入待确认台账。
3. **形成结果：** 优先在已有文件的正确章节维护；新主题才创建新文件。保持来源、建议和确认状态可辨认。
4. **同步：** 依据变更性质处理受影响文件。无证据的状态不更新为已确认或已完成。
5. **检查与交接：** 核对产物内容、引用和文件位置；更新实质变化及下一步，给用户可点击入口。

这些步骤随当前任务执行，不要求用户逐步批准常规整理，也不构成后台自动化。

## 3. 状态和证据

- 需求内容：文档共识／候选方案／AI建议／待确认。新的人工作出的明确决定需记录确认人或确认来源、日期和影响；不得虚构姓名。
- 管理任务：待开展／进行中／待输入／已完成／已取消。已完成必须有交付物或结果依据；建议事项不等同于已安排任务。
- 待确认问题：待确认／已解决／暂缓／已取消。解决后关联决策或其他明确答复，保留问题历史。
- 产物成熟度：草稿／待评审／已确认／已替代。另行记录实现、测试、验收状态，不把文档成熟度当作功能上线状态。
- 旧共识提取为台账时注明“继承文档共识”，不补造当时确认人、时间或会议记录。来源有冲突时保留冲突并询问。

## 4. 变更同步

| 触发变化 | 必须核对 |
|---|---|
| 用户确认新业务规则或调整范围 | 决策依据 → 共识主本 → 相关需求条目；有对应设计、原型、评审时再同步 |
| 发现材料缺口或相互矛盾 | 资料索引的阅读状态、Q条目的问题与影响；不直接覆盖既有共识 |
| 需求设计或原型调整 | 对应R编号、说明和验收口径；演示行为不自动成为正式规则 |
| 实际评审、排期或交付结果 | 对应正式记录和证据、项目状态；不从口头设想推算承诺日期 |
| 文件移动或改名 | 首页、文内链接、资料索引和相关记录；尽量整体移动原型及其依赖 |

未能同步时，在对应决策的同步状态或工作记录写明差异、原因与下一步。不要声称全部对齐。

## 5. 命名与保存

- 长期维护主本使用稳定名称，如“业务流程与需求共识.md”；日期和版本写在正文，避免反复创建“最终版2”。
- 会议录音原文与整理纪要统一保存到 `01_业务资料/会议纪要/`，使用 `主题_YYYY-MM-DD_HHmm_原文.md` / `主题_YYYY-MM-DD_HHmm_纪要.md`。时间依据、未知时间及同名处理见[会议归档规则](../01_业务资料/会议纪要/README.md)；原文保持内容原貌。
- 其他一次性事件使用 `YYYY-MM-DD-主题-记录类型.md`。文件名日期必须有实际依据。
- 专题设计或原型可用 `R06-课程目录/` 或带同一需求编号的文件名。只有产生相关工作时才建立子目录。
- 新文档至少说明日期、状态和依据；有未决项则关联Q编号。原始材料保持内容原貌，解读另存。
- 文档内优先用相对链接以便整体迁移；向用户交付时使用绝对文件链接。
- 重要内容在大幅替代前保存必要快照到 `99_归档/`，记录原位置、归档原因和当前替代稿；普通文字修正不制造整套备份。
- 不存储账号密码、访问令牌等秘密。资料访问和对外传播范围遵循用户授权。
- 所有本项目经验先放在本地合适位置；不默认创建或修改全局技能、记忆、钩子或自动化。

## 6. 轻量记录模板

2026-09-15流程顺序补充：第4步保留独立需求评审文档，第5步先确定sprint排期，之后才录入禅道需求和任务。必须同时依据已审核评审文档及已确认排期表；本次排期的每个评审需求对应一条禅道需求，多条排期任务关联同一需求。不得在录入阶段再自行拆分、创建额外汇总父需求；未排期、来源缺失或冲突先处理，不提前写入。

禅道需求、子需求和任务按[产品工作流创建标准](C:/Users/Administrator/.codex/skills/pm-workflow/references/zentao.md)处理：先展示每条实际提交正文、验收、图和目标位置，审核绑定版本和条目，再按用户写入授权执行。任务范围与安排单独确认；创建/拆分指令不能替代未展示正文的审核。“不复查详情”仅豁免写后核验。确认后只做不改语义的格式转换，实质变化部分重新审核；人员、工时及日期不擅填。相同已确认内容和授权不重复索取批准。用户已明确既有禅道数据不处理，本次流程维护不触发历史修改。

以下模板按需取用，不必为每个小任务创建独立文件。

**业务沟通纪要：** 日期与参与者（未知则如实标记）；原始材料；观察事实；明确决定；待确认问题；受影响R编号和文档；实际约定的下一步。

**功能设计：** 关联需求与依据；状态；目标与范围；流程和规则；异常与权限边界；验收口径；Q编号。只写有依据或清楚标注的建议。

**工作记录：** 日期与编号；任务与授权依据；产物或改动；实际验证；未决项；下一步。

## 原型预览交付归档

原型部署产物按需求归档为 `06_交付与验证/<需求名称>原型预览/`，内部再放局域网预览服务、离线包与核验记录，不直接将通用名称的服务文件夹散放在交付根目录。同一需求跨多个页面时统一归档；不同需求使用独立目录，核对端口/任务归属。当前实例为“内容协作系统原型预览”。迁移时必须同步运行任务、发布依赖、防火墙程序路径与文档链接，验证原访问地址及后续更新可用。

效果图交付目录采用“需求名称-产物类型-版本”，如“内容协作智能体-Figma效果图-v1”；页面编号可以作为辅助信息，不单独依靠工具名和页面编号表达需求归属。
