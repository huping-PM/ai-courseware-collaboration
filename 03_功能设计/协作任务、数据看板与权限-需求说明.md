## 1. 已明确要求与方案边界

| 主题 | 用户已明确 | 本稿补充的建议，待确认 |
|---|---|---|

用户认为当前需求已满足基本创作要求，这是对需求覆盖的判断，不作为系统已完成或已验收的证据。本轮补充协作管理，不重新定义已有内容创作能力。

员工完成创作的标准为提交任务审核，主管审核通过后任务完成并计入成品数量（D043）。提交不是完成或计数前提；撤回/作废后的统计处理仍待Q20。技能更新申请仍须主管审核通过，两类审核对象及记录不可混用。

建议采用“制作任务关联现有会话”：复用AI创作界面，以任务串联人员、交付物和过程数据。仅给会话加负责人虽改动少，但无法完整表达派工、验收及交付统计；新增多阶段流程编排虽细致，但会引入尚未确认的固定生产环节。因此本稿采用前者作为待评审设计。

## 2. 业务对象与整体流程

- **制作任务**：主管布置的工作，记录要求、负责人、交付物和业务状态。
- **创作会话**：员工与AI对话的上下文；现有左侧“会话任务列表”继续承担切换与并发查看。
- **生成执行记录**：一次模型或工具执行及其耗时、用量、状态；完成一次生成不等于完成制作任务。
- **成品课件**：员工提交审核并由主管审核通过的业务交付物，审核通过后计数；建议提交前校验约定的文件及交付项是否齐全。图片、脚本、中间视频、重复导出不自动成为一份成品。

建议关系：一个制作任务可关联多个创作会话；一个会话只归属一个制作任务；每次执行及交付版本可回溯到任务、项目与实际操作者。已有关联和用量的会话不直接改绑任务，防止历史归属被重算。无任务的自主创作是否保留、如何补关联见Q19；暂不把所有聊天强制改为先建任务。

主流程：主管创建并分配 → 员工收到待办 → 查看要求并开始创作 → 进入绑定任务的AI协作界面 → 持续记录活动与调用 → 员工选择成品提交审核 → 主管审核通过 → 任务完成且成品数量计入看板；审核退回后，员工继续创作并重新提交。

派工、从任务进入创作、记录数据及主管审核通过后完成和计数均已明确；成品唯一标识、修订去重及撤回处理待Q20。制作任务审核和技能更新申请审核分别留存记录。

## 3. 制作任务管理（R07，关联R05/R06/R08）

### 3.1 入口与创建

在项目内新增“任务管理”模块，分为“我的任务”和“全部任务”。按D049，项目管理员添加、编辑、分配当前项目任务；项目成员仅能查看分配给自己的任务，不能通过搜索、筛选或直达链接获取他人任务，并可从任务进入AI协作智能体。原D044关于主管审核、删除、归档和查看全部任务的要求仍保留，哪些项目管理员拥有这些能力待Q22确认。站内待办提示新分配、改派、提交和审核意见为设计建议；外部消息渠道不预设。详细任务主线以[任务管理需求说明](任务管理-需求说明.md)为准。

创建表单建议包含：任务名称、所属项目、制作目标/受众、交付要求、参考资源、负责人；截止时间和优先级按需填写，不虚构工时或固定交付格式。任务编号、创建人和创建时间由系统生成。若一个任务允许多个课件，需明确交付清单与每个成品的独立标识，不能把任务数当课件数。

负责人必须属于可管理下属范围，并具备该项目访问权限且账号可用。缺少项目权限时提示处理成员关系，不因分配自动获得其他项目数据权限。任务发布与分配记录一致后才发送待办，重复提交不得产生重复任务或通知。主管编辑任务时保留前后内容和时间；员工进入创作后，主管修改交付要求需提示员工并记录版本，避免以新要求审核旧提交。

### 3.2 状态与流转建议

| 状态 | 操作与操作者 | 后续状态及限制 |
|---|---|---|
| 草稿 | 主管保存或发布并分配 | 草稿不进入员工待办；发布成功为待开始 |
| 待开始 | 负责人点击开始创作 | 创作中；首次开始时间只记录一次；仅查看详情不算开始 |
| 创作中 | 负责人选择成品版本并提交审核 | 待审核；生成失败属于执行状态，不自动取消任务 |
| 待审核 | 主管审核通过或填写意见退回 | 已完成并计入成品数量，或待修改；审核对象固定为本次提交的版本快照 |
| 待修改 | 负责人进入原任务继续修改 | 创作中；保留退回原因、历史提交及全部耗用 |
| 已完成 | 查看成品、审核及过程证据 | 修改须由有权限人员重开并保留原因；重新提交和审核不得覆盖原完成记录 |
| 已归档 | 主管归档已完成或不再推进的任务 | 默认不在常规列表显示，可按归档筛选查看；不再允许创作或审核，恢复规则待Q25 |
| 已取消 | 主管取消未完成任务并填写原因 | 停止新创作；已有消耗和过程记录保留，已发生消耗不能归零 |

逾期由截止时间与状态计算为标记，不单独增加互斥状态。主管删除草稿任务时可执行逻辑删除；已发布、已有创作记录或已审核的任务删除后不再在常规列表显示，但过程记录、统计和审计证据保留，避免 KPI 数据被物理抹除。删除可否恢复和归档/取消的使用边界见Q25。暂停及协同多人编辑是否需要见Q19，不在本稿擅定复杂流程。

### 3.3 进入AI协作界面

- 从任务点击开始/继续创作，传递项目和任务上下文，展示任务名称及返回详情入口；不改变现有会话列表单行名称＋状态图标规则。
- 首次进入可创建绑定会话，续做进入该任务已有会话；任务要求作为明确的上下文材料，员工可查看来源。切换会话时同时核对绑定任务，不能沿用上一个任务的计时或归属。
- 内容、调用、上传和提交分别关联当前任务；由后台运行产生的Token仍归属发起执行的任务及实际操作者，不能按回调时当前打开的页面归属。
- 选择成品提交审核时保留文件/成果标识、版本、提交人、时间及说明。保存到资源库与提交审核是独立动作，前者不自动计数或完成任务。

### 3.4 异常与历史

- 改派仅允许主管在授权范围内操作并记录原因；已发生的个人活动和Token保留原操作者归属，不整体算给新负责人。成品贡献分配见Q21。
- 员工离职、账号停用或项目权限撤回后阻止新的访问和提交，主管可处理改派；保留历史证据。执行中的生成如何取消或接续需研发核对，已发生用量持续归账。
- 待审核期间员工可准备后续草稿，但不得悄悄替换提交快照；撤回和重提需保留记录。重复点击提交或审核只产生一次有效状态变更；仅审核通过产生一次计数事件。
- 技能停用、接口失败、断线及并发执行不抹去成功成果；执行失败与人员未完成分开展示，避免把服务故障直接视为员工绩效问题。

## 4. 计量口径与KPI证据（R19）

以下为推荐计量设计，具体阈值和业务口径待Q20/Q21确认。

| 指标 | 建议定义 | 解释与边界 |
|---|---|---|
| 平台内有效创作时长 | 按实际操作者累计与任务相关的有效活动区间 | 根据编辑、对话、成果处理等活动及在线心跳识别；后台挂机、长时间无活动不持续计时，空闲阈值待定。平台外工作单列申报/佐证，是否支持待确认 |
| 首次输出成品耗时 | 首次主管审核通过时间－首次开始创作时间 | 自然经过时长，包含等待与返工；仅生成中间文件或提交待审核不结束计时 |
| 最终交付耗时 | 最后一次主管审核通过时间－首次开始创作时间 | 包含此前修改及AI等待；重开后再次通过的处理待Q20 |
| 任务总周期 | 完成时间－派发时间 | 额外包含员工开工前排队，可用于主管分析安排，不直接归因员工效率 |
| AI执行/等待时长 | 每次执行的排队时间、运行时间分别记录 | 并行调用时执行累计时长可能大于自然经过时长；不可再加到人工有效时长称总工时 |
| Token消耗 | 按唯一调用记录汇总服务返回的实际输入、输出及总用量 | 保留模型和供应方；缓存及推理字段按接口语义记录，不重复叠加总量。失败、重试实际已消耗的Token保留 |
| 成品课件数量 | 主管审核通过后计入（D043）；建议按独立课件标识去重 | 一个课件的多次导出、修订版建议不重复增数；成品与任务可以一对多，具体粒度待Q19/Q20 |
| 返工情况 | 退回次数、原因、追加创作时长及用量 | 不预设“返工必然扣分”；质量、需求变化及系统故障原因应能区分 |

### 4.1 多会话、多人和不完整数据

- 同一人在同一任务多个标签页/设备上的重叠活动区间合并；在不同任务间仅给明确处于活动状态的任务计时，冲突区间标待核对，不能双算个人工时。
- 若后续允许多人参与，每人投入分别记录；任务人工投入为各人有效时长之和，任务自然耗时不按人数相加。
- 每次调用使用稳定唯一标识处理回调重复、网络重试和补报；一次真实重试是新的消耗记录，同一次调用重复回调不能再次累加。
- 不返回Token的图像/视频/语音服务，记录调用次数、生成秒数等原生用量，Token标“未提供”，不得填0或自行换算；费用统计仅在有价格和计费证据后另行设计。
- 展示数据完整性、待补报记录及最后更新时间。补报更正保留前后值、原因、操作者和时间，重算相关汇总，禁止静默覆盖已使用的证据。

### 4.2 可追溯证据

任务详情提供过程记录：派发/改派历史、活动区间、会话与执行记录、模型用量、成品版本、提交、审核及修改记录。员工能查看自己的记录并提出异议；更正权限及复核流程待Q21。

指标用于支撑管理判断。Token高低或用时长短不自动等于贡献高低，不设计未经确认的评分、排名、薪酬或奖惩公式。建议结合成品质量、任务复杂度与返工原因解释数据。

## 5. 课件协作数据看板（R19）

### 5.1 展示与筛选建议

| 区域 | 内容 |
|---|---|
| 核心指标 | 成品课件数、平台内有效创作时长、Token总量、平均首次输出成品耗时；缺失用量数量及统计更新时间 |
| 任务概况 | 待开始、创作中、待审核、待修改、已完成、已取消及逾期任务数 |
| 趋势 | 按日/周/月展示产出、人工投入与Token消耗，不把不同单位画成同一数值序列 |
| 团队明细 | 员工、成品贡献、有效时长、Token、已完成任务数、首次成品耗时、修改情况；默认明细表，不预设绩效排行榜 |
| 用量分析 | 项目、人员、模型、技能/版本和执行状态；多技能调用不得把同一调用总Token全额重复分给每项技能，无可靠分摊数据时标为组合调用 |
| 下钻 | 指标 → 任务/课件明细 → 提交、活动或调用原始记录；导出沿用相同权限和统计口径 |

### 5.2 项目成员任务统计

按当前项目和筛选期间，以成员为行展示：任务总数、待开始/创作中/待审核/待修改/已完成任务数、已归档和已取消任务数、平均完成任务时长、Token流量、任务完成率，以及一次、二次、三次审核通过数和对应通过率。员工仅能查看本人行及本人明细；主管查看当前项目全部成员及任务明细。

建议口径如下：

| 指标 | 分子 | 分母/时间归属 |
|---|---|---|
| 平均完成任务时长 | 每个已完成任务的主管审核通过时间－首次开始创作时间之和 | 统计期间审核通过的任务数；无已完成任务显示“暂无数据” |
| Token流量 | 成员在当前项目任务下的实际调用Token总量 | 按实际调用时间落入期间；失败或重试已消耗用量保留，重复回调不重复累计 |
| 任务完成率 | 统计期间审核通过的任务数 | 统计期间应完成任务数；应完成任务的时间归属及未设截止时间的处理见Q24 |
| 一次审核通过率 | 第一次进入待审核即通过的任务数 | 同期应完成任务数 |
| 二次审核通过率 | 第二次进入待审核后通过的任务数 | 同期应完成任务数 |
| 三次审核通过率 | 第三次进入待审核后通过的任务数 | 同期应完成任务数 |

一次、二次、三次审核通过率均是任务完成率的分项，不与总完成率重复相加；三次以上审核通过单列“≥四次审核通过”，不可丢入三次数据。审核退回次数按同一任务连续记录，主管重复点击审核不增加审核次数。任务被改派时，完成任务与审核通过率按审核通过时的负责人统计；历史创作时长和Token仍归原实际操作者，避免将两个不同维度混为同一人贡献。

筛选维度建议为日期范围、当前项目内成员、任务状态、审核次数、模型及技能版本；项目为当前固定上下文，不提供跨项目合并。不存在业务来源的课件类型/难度不伪造枚举。员工默认只看个人数据，主管看当前项目全部成员及任务；导出权限见Q22。

### 5.3 时间与汇总口径

- 默认“期间产出与消耗”：成品数按首次主管审核通过时间落入期间，有效时长按活动与期间相交部分，Token按实际调用发生时间；跨日调用先约定统一归属时间并展示口径，迟到回调回补原期间。
- “完成任务成本”作为另一分析口径时，只筛选期间首次审核通过的任务，再汇总其全生命周期时长和Token。不得与“期间消耗”混作同一个平均单课成本。
- 平均首次输出成品耗时建议按期间首次审核通过任务的耗时求均值；一个任务多个课件不能据此标为平均单课耗时。未完成任务另显示截至统计时刻的已用时。
- 主管、部门及组织调整保留历史归属快照；统计按历史还是当前组织归属见Q21。跨部门贡献应避免成品重复计数，人员贡献与团队去重总数分别解释。
- 同一课件继续修改不增加课件数量，首次与后续提交及审核均留记录。撤回、作废和跨期更正策略待Q20/Q21，不能删除历史后假装从未通过。
- 筛选、卡片、图表、明细和导出使用同一口径；空数据不等于采集失败，缺失数据不展示为零。

## 6. 账号与模块权限（R11/R18）

建议权限同时考虑“操作权限＋管理范围＋项目授权＋对象归属”。部门主管身份不自动开放所有项目和其他部门数据。组织/上下级关系来源、兼任主管与离职同步待Q22。

下表除技能编辑更新及申请审核方向外，均为待评审权限建议；系统管理员是账号配置角色建议，不因其身份自动取得主管业务审批权。

| 模块/操作 | 员工 | 部门主管 | 系统管理员（建议） |
|---|---|---|---|
| 任务管理 | 仅查看和执行分配给本人的任务，提交任务审核 | 在当前授权项目查看全部任务，创建、编辑、审核、删除、归档、改派和取消；审核通过后任务完成并计数 | 配置权限，不默认参与业务审批 |
| AI协作与成果 | 本人任务/获授权会话创作及提交 | 查看管理范围内任务过程和交付物；参与创作需相应权限 | 不默认读取所有对话 |
| 资源管理 | 查看/使用项目授权素材；上传、修改本人素材为建议 | 管理获授权项目素材；被引用删除仍受保护 | 维护权限配置，不绕过项目隔离 |
| 项目技能启用 | 查看可用技能，使用项目已启用技能 | 建议由获授权主管维护项目启用关系 | 维护授权配置 |
| 全局技能内容 | 查看/使用获授权内容、提交更新申请；无直接更新权 | 仅获全局技能维护授权的主管编辑更新及审核申请 | 不因系统管理员身份自动获得技能编辑权 |
| 提示词 | 建议查看使用、提交修改意见 | 建议维护授权项目提示词 | 维护授权配置；是否套用技能申请流程待Q22 |
| 数据统计 | 查看本人数据及证据为建议 | 查看当前项目全部成员任务统计及明细；导出另设权限 | 不默认拥有全公司绩效数据权限 |
| 项目设置/成员 | 查看允许公开的信息 | 项目管理权限另行授予，不由部门职务自动取得 | 按系统授权管理 |
| 账号/角色/导航/资源集 | 无系统维护权限 | 不默认拥有账号或权限配置权 | 专门授权维护；资源集不产生跨项目访问豁免 |

权限应作用于列表、详情、搜索、预览、下载、导出、写入及后台执行，不能只隐藏按钮。用户无权为自己提权；角色变化后的权限刷新、执行中任务处理与审计需覆盖。角色不足与数据不存在分别给出合适反馈，避免泄露未授权对象内容。

## 7. 技能更新申请与审核（R10）

继承D039：技能定义仍全局唯一维护，项目只按需启用；本次没有改成部门各维护一套。员工申请提出变更，不直接修改已生效技能。

建议流程：员工从全局技能详情或项目技能详情发起更新申请 → 填写修改原因、基于版本、拟更新内容/技能包和验证说明 → 提交至有权主管 → 主管查看新旧差异、关联附件与影响项目 → 驳回填写原因，或通过并发布新版本 → 员工收到结果，历史申请及版本可追溯。

- 申请状态建议：草稿、待审核、已驳回、已撤回、已通过待生效、已生效、生效失败。通过表示审批结论，不伪装成更新已经成功。
- 待审核内容形成快照，不可提交后偷改；修改应撤回后重新提交。主管直接编辑也记录变更人、原因、前后版本；是否需要第二人审核不自行加入必需步骤。
- 主管审核前发现基于版本已过期，展示冲突并要求重新核对，不能直接覆盖别人已发布的更新；同一申请重复处理不能发布多个版本。
- 审核通过与生效失败分开处理；发布失败保持旧版可用并显示重试/处理入口，申请不得自动变为“已生效”。
- 建议执行记录固定实际使用版本，更新只作用于后续新执行；已在运行的执行及历史成果保留旧版本证据。会话后续执行是否统一切新版见Q16/Q23。
- 全局更新可能影响多个项目，审批页应显示影响范围。下属申请是否由直属主管还是技能负责人主管审批、跨部门主管的维护边界见Q23；不直接假定所有主管都可改全局技能。
- 技能新增、停用、删除、回滚是否同样仅主管可操作，以及申请内容校验和试用方式，保留Q16/Q23核对。脚本等附件沿用现有技能包保留要求。

## 9. 建议验收场景

1. 主管只能向可管理且具备项目权限的员工分配；员工收到任务后进入正确项目/任务，其他员工及其他项目直达链接不能越权读取。
2. 同一制作任务能续做原会话并关联其他会话；切换任务后执行、用量和成果归属正确。AI执行成功不直接把制作任务置为完成。
3. 未选择有效交付物不能提交；员工提交后进入待审核，主管审核通过后任务完成并计入成品数量；保留提交和审核快照；重复提交、重复审核及修改版本不增加同一课件数量（去重细则待评审）。
4. 员工仅能在“我的任务”看到分配给本人的任务；主管能在当前项目“全部任务”创建、编辑、审核、删除、归档和查看全部任务，直达链接与接口同样受限。
5. 用含空闲、跨日、双标签页与并发AI调用的样例核对：个人有效时长不双算，自然耗时与执行累计时长分别正确。
6. 调用失败但已返回实际用量仍计消耗；重试真实新调用分别计入，重复回调只计一次；用量缺失标未知并能补报追溯。
7. 成员统计的平均完成时长以审核通过时间计算；一次、二次、三次及≥四次审核通过任务分别统计，主管重复操作不增加审核次数。
8. 改派前后的个人贡献可区分；取消、归档或逻辑删除任务不清空历史耗用和审计记录，完成课件归属按最终确认规则执行。
9. 看板在相同筛选下与明细、导出一致；跨月完成任务的期间消耗与生命周期消耗能明确区分，平均值不会混用分子分母。
10. 员工不能直接更新技能，即使直接调用接口也被拒绝；申请未通过不影响当前技能，发布失败保留旧版，过期申请不能覆盖新版。
11. 权限撤回后新访问/操作被阻止，后台执行按已确认策略处理；主管仅见授权范围数据，系统管理员身份不默认绕过业务权限。

## 10. 待确认与评审顺序

问题状态统一维护在[决策与待确认](../00_项目管理/决策与待确认.md)，本节只说明影响，不另维护一套结论。

- **Q19 任务与协作粒度**：一任务一人还是允许多人；能否多课件；自主创作及补关联；影响对象关系和入口。
- **Q20 成品计数细则**：主管审核通过后任务完成并计数已由D043确认，不再待选；只核对成品唯一标识、修订去重及撤回/作废的计数调整。
- **Q21 计量与贡献**：有效活动阈值、平台外工作、改派/组织变化、数据更正及统计结算；影响可信度与可比性。
- **Q22 权限与部门范围**：组织来源、主管管辖、跨项目看板、其他模块权限、导出；影响项目隔离与角色配置。
- **Q23 全局技能审批**：有权主管、跨部门范围、版本冲突与生效；影响所有启用项目，关联Q16。
- **Q24 任务完成率口径**：统计期间“应完成任务”的时间归属、无截止时间和跨期任务的处理，以及是否以任务派发、到期或审核通过为统计范围。
- **Q25 任务删除与归档**：逻辑删除的恢复期限、归档/取消/删除的边界、被删除任务是否允许恢复及历史统计展示方式。

主管审核通过后完成和计数已确认。建议接着确认任务粒度、成品去重和撤回规则，再确认数据范围和技能审核负责人，最后细化计时参数及看板布局。以上顺序为评审建议，未锁定首版范围、负责人、工时或上线日期。
